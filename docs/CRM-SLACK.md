### 1-5. 스크래퍼 셀렉터

`automation/studiomate/selectors.mjs` **한 파일만** 고치면 된다. `scrape.mjs` 는 흐름만 담당하고
셀렉터를 전혀 모른다. 2026-08-10 기준으로 이미 실제 값이 채워져 있다.

화면 흐름:

```
/schedule (일간·룸별)  →  .event-item 클릭  →  /lecture/detail?id=…  →  뒤로
```

- **날짜는 URL 쿼리(`?date=`)로 못 바꾼다 — 무시된다.** 좌/우 화살표로만 이동하며,
  `gotoDate()` 가 현재 날짜를 읽어 목표까지 한 칸씩 이동하고 매번 검증한다.
- **수업 상세 한 페이지에 필요한 게 전부 있다** — 이름·연락처·수강권명·잔여횟수·수강권기간·
  예약상태. 회원 상세 모달에 따로 들어가지 않는다.
- **전체횟수는 화면 어디에도 없다**("12회 남음"만). 그래서 스크래퍼는 전체횟수를 빈 값으로
  보내고 `apply_attendance` v2 가 `coalesce` 로 DB 기존 값을 유지한다. 전체횟수는 등록 시점
  확정값이고 주간 엑셀 재업로드로 교정되므로 매일 갱신할 필요가 없다.
- 예약상태는 텍스트가 아니라 **readonly `input` 의 value** 다(Element UI 셀렉트).
  화면 원문: `예약` · `예약 확정` · `예약 대기 (1)` · `출석` · `결석`
  → `normStatus` 가 `예약 / 예약대기 / 출석 / 결석 / 노쇼 / 취소` 로 접는다.
- 예약자 행은 반드시 `li.members-list-item` 으로 잡는다 — `li` 만 쓰면 상태 드롭다운 옵션까지
  잡혀서 11명짜리 수업이 55개가 된다.

```bash
# 창을 띄워 놓고 직접 확인
HEADLESS=false ONLY_BRANCHES=광교 DRY_RUN=true node automation/run.mjs
```

셀렉터 값은 문자열(CSS), 함수(`async (scope) => string`), `null`(아직 모름) 셋 다 된다.
`null` 이면 그 필드만 비고 실행 요약에 `못 읽은 필드` 경고가 뜬다.

### 1-6. 예약대기 (2026-08-12 실측 · 27개 수업 전수 확인)

수업 상세의 회원 목록은 **한 덩어리가 아니다.**

```
div.lecture-members
  h5 "예약회원 (11명)"                                  ← N
  div.lecture-members__list > ul > li.members-list-item   예약자
  h5 "예약 대기 회원 (2명)"                              ← M (대기자가 있을 때만 있음)
  div.lecture-members__list > ul > li.members-list-item   대기자 (별도 ul)
  h5 "예약 취소"                                         (표본 27개에선 행이 0개였다)
```

- 🔥 **라벨 N ≠ `li` 수.** 정확한 불변식은 **`count(li:not(.uncounted)) == N + M`** 이다.
  - **결석 행에는 `uncounted` 클래스가 붙고 라벨 N 에서 빠진다** (결석 ⇔ `uncounted` 1:1, 예외 0건).
  - 대기자는 자기 라벨 M 으로 따로 센다.
  - 이걸 몰라서 만석 수업이 "화면은 10명인데 11명이 읽혔습니다"로 실패했다.
- 대기자 `li` 에는 **구분용 클래스가 없다** — 예약자와 똑같다. 구분은 예약상태 값으로만 한다.
- 대기자는 `reservations` 에 `예약상태='예약대기'` 로 **남기고**, CRM 대상에서만 뺀다
  (`shared/crm-rules.mjs` 의 `NOT_ATTENDING`). 대기자에게 "내일 봬요" 멘트가 나가면 안 된다.
- ✅ **대기 → 출석 전이는 다음날 스스로 확인된다.** 대기자와 확정자는 `res_key` 가 같아서,
  승격돼 수업에 들어가면 D-1 스크랩이 같은 행을 `예약대기 → 출석` 으로 덮는다.
  (실측: 8/13 20:00 수업에서 몇 시간 새 예약 10→11 · 대기 2→1 로 승격이 일어났다.)
  그래서 `save_reservations` 의 `on conflict` 는 `예약대기` 를 `예약` 과 같은 **미확정**으로 본다.
- 실행 로그에 `· 그중 예약대기 N명(CRM 제외)` 이 찍힌다 — 몇 명이 빠졌는지 매일 보인다.

### 1-7. 과거 예약 백필 — "14일 미방문"을 첫날부터

휴면 규칙은 예약 스냅샷이 쌓여야 동작한다(`관측일수 = current_date - min(예약일자)`).
매일 실행만으로는 14일을 기다려야 하는데, 스튜디오메이트는 **과거 날짜를 조회할 수 있어서**
그 14일을 미리 채울 수 있다.

```bash
# ① 먼저 dry-run 으로 건수만 (저장 안 함)
DRY_RUN=true npm run backfill

# ② 실제 저장. 기본은 "어제부터 14일" — 30일치를 권장한다(여유 있게)
DRY_RUN=false BACKFILL_DAYS=30 npm run backfill

# 기간 직접 지정 / 한 지점만
DRY_RUN=false BACKFILL_FROM=2026-07-15 BACKFILL_TO=2026-08-11 npm run backfill
DRY_RUN=false ONLY_BRANCHES=광교 npm run backfill
```

- ⛔️ **백필은 `reservations` 만 채운다 — `apply_attendance` 를 부르지 않는다.**
  수업 상세의 "12회 남음"은 그 날짜의 값이 아니라 **회원의 현재 잔여횟수**다. 과거 날짜를
  돌며 members 를 갱신하면 같은 값을 수백 번 덮어쓸 뿐이고, 중간에 실패하면 어디까지
  반영됐는지도 알 수 없다. 출석 반영은 매일 도는 `run.mjs` 가 D-1 에 대해서만 한다.
- **오늘·미래 날짜는 거부한다.** 내일 예약은 `run.mjs` 의 roster 단계가 맡는다.
- **중단해도 안전하다.** 끝낸 (사이트,날짜)를 `automation/out/backfill-progress.local.json`
  에 남겨 재실행 때 건너뛴다(`RESET_PROGRESS=true` 로 초기화). 실패한 날짜는 기록하지
  않으므로 그대로 다시 돌리면 그것만 재시도한다. dry-run 은 진행 파일에 아무것도 안 남긴다.
- 시간이 꽤 걸린다 — 날짜마다 전 수업 상세를 연다. 사이트를 바깥 루프에 둬서 로그인은
  사이트당 1회고, 날짜는 화살표로 한 칸씩만 움직인다(`navigate:false`).
- 끝나면 관측일수를 확인한다: `npm run db:sql sql/2026-08_verify_crm.sql`

### 1-8. 🔥 조용히 틀리는 자리 — 스크래핑 5대 결함

2026-08-12 백필을 **실제로 돌려 보고서야** 다섯을 찾았다. 공통점이 있다:
**전부 에러 없이 초록불로 끝났고, 인원수 검증도 통과했다.**

| # | 결함 | 실측 피해 | 고친 방법 |
|---|---|---|---|
| 1 | `"예약 대기 (1)"` 을 `'예약'` 으로 정규화 | 만석 수업 대기자에게 멘트 발송 | `STATUS_RULES` 에 `예약대기` 를 `예약` **앞**에 |
| 2 | 행마다 `nth(i)` 로 왕복 읽기 | 옥수 07-29 에서 **8명 증발**(44행 읽고 35명) | 목록을 `page.evaluate` 한 번으로 통째로 |
| 3 | 클릭 직후 상세를 그 자리에서 읽기 | 솔쌤10:30 **수업 하나가 통째로 증발**(10명) | `URLS.lectureDetail(slug, id)` 로 새로 열어 읽기 |
| 4 | 라벨을 못 읽으면 검증을 **건너뜀** | 8명짜리 수업이 0명으로 나가 07-31 이 94→86 | 라벨을 기다리고, 못 읽으면 **실패**시킨다 |
| 5 | 헤더 컨테이너만 보고 제목을 읽음 | **수업명 빈 행 73건** + 수업시간에 스크랩 시각 | 제목이 채워질 때까지 기다리고, 날짜도 대조 |

결함 4 가 특히 고약하다. `예약N` 이 `NaN` 이면 `if (Number.isFinite(예약N))` 이 거짓이라
**검증 자체가 사라지고**, 아직 안 그려진 빈 목록이 "예약자 0명"으로 나간다. 0행이라
중복 검사에도 안 걸려 흔적이 남지 않는다.
→ **검증을 조건부로 만들지 말 것.** 검증할 수 없으면 통과가 아니라 실패다.

결함 5 는 결함 3·4 와 같은 뿌리다 — **`detail.ready` 는 헤더 "컨테이너"만 보장한다.**
그 안의 제목·일시는 데이터가 온 뒤에 채워진다. 바로 읽으면
`수업명 = ''` 이라 `res_key` 가 정상 행과 달라져 **별개 행으로 쌓이고**, 일시 파싱이
엉뚱한 값을 집어 **수업시간에 스크랩이 돌던 시계 시각**(18:49, 19:02 …)이 들어간다.
DB 에 `예약일자=오늘 · 수업명='' · 수업시간=18:49` 인 행 73건이 그렇게 생겼다.
→ **"요소가 있다"가 아니라 "값이 채워졌다"로 판정할 것.** 그리고 상세의 날짜가
  목표 날짜와 같은지도 대조한다(다르면 엉뚱한 날에 출석이 기록된다).

**⚠️ 검증을 엄격하게 만들 때 "정상인데 검증 대상이 없는 경우"를 반드시 구분할 것.**
결함 4 를 고치며 "라벨을 못 읽으면 실패"로 바꿨더니, **예약자가 0명인 수업**에서 걸렸다.
그런 수업엔 `"예약회원 (N명)"` 라벨이 **아예 없다**(라벨이 `수강회원`·`예약 취소` 뿐, li 0개 —
실측 2026-08-13 광교 11:00·19:00). 빈 수업 하나가 그 지점 스크랩 전체를 실패시켜
**광교·반포 명단이 통째로 빠졌다.** 엄격한 검증이 되레 CRM 을 끊은 것이다.
→ 구분 기준은 `li` 개수다. 라벨 없음 + li 0개 = 진짜 0명(정상),
  라벨 없음 + li 있음 = 앞뒤 안 맞음(실패). 헤더 제목을 이미 기다렸으므로 데이터는 도착한 뒤다.

**정리(clean-up).** `reservations` 는 전부 재수집 가능한 파생 데이터다. 위 결함들이 남긴
행이 섞였다면 기간을 통째로 지우고 다시 채우는 게 가장 깨끗하다 —
[sql/2026-08_reset_reservations.sql](../sql/2026-08_reset_reservations.sql) 로 지우고
`npm run backfill` 로 다시 채운다. 지우기 전 `npm run db:backup reservations`.

**왜 검증을 통과했나 — 여기서 배울 것**

1. **개수 검증은 정체성 검증이 아니다.**
   `count(li:not(.uncounted)) == N + M` 은 **몇 개인지**만 본다. 같은 사람을 두 번 읽고
   다른 사람을 빠뜨려도 개수는 맞다. 결함 2·3 이 이걸로 다 통과했다.
   → 개수를 셌으면 **누가 들어 있는지**도 봐야 한다(중복 키 검사).
2. **SPA 에서 "값이 있다"는 "그 값이 최신"과 다르다.**
   결함 3 은 로딩 판정 요소가 **직전 화면 것이 남아 있어서** `waitFor` 가 즉시 통과했다.
   → 요소의 **존재**가 아니라 **내용이 기대한 대상과 일치하는지**로 판정하거나,
     아예 URL 로 새로 로드해 대상을 못 박는다.
3. **줄어든 건수는 사유와 함께 찍는다.**
   `save_reservations` 는 `parsed`·`duplicates` 를 돌려주는데 백필 로그가 그걸 안 찍고
   "저장 45건"만 찍었다. 7건이 사라진 걸 아무도 못 봤다.
   → 수집 ≠ 저장이면 **왜** 줄었는지 반드시 로그에 남긴다.
4. **같은 입력을 2~3회 돌려 같은 값이 나오는지 본다.**
   결함 2·3 은 전부 **비결정적**이었다(07-29 가 75/77/77, 중복 0~11건). 한 번만 돌리면
   "정상"으로 보인다. 셀렉터나 순회 로직을 고쳤으면 **반드시 반복 실행으로 확인한다.**

```bash
# 결정성 확인 — 같은 날짜를 3회 돌려 건수가 같은지 본다 (저장 안 함)
for i in 1 2 3; do
  DRY_RUN=true RESET_PROGRESS=true ONLY_BRANCHES=청담,판교 \
    BACKFILL_FROM=2026-07-29 BACKFILL_TO=2026-07-29 npm run backfill
done
```

**새 목록·새 화면을 추가할 때 지킬 것**

- 목록은 **한 번의 `evaluate`** 로 읽는다. 행마다 왕복하지 않는다.
- `selectors.mjs` 의 행 내부 셀렉터는 **`li` 기준 하위 CSS 문자열**이어야 한다
  (함수로 두면 브라우저 안으로 넘길 수 없다).
- 상세 화면은 **URL 로 직접 연다.** 클릭은 id 를 알아내는 용도로만.
- 식별자를 못 읽으면 **폴백 키를 만들지 말고 실패시킨다.** 폴백은 같은 대상을 두 키로
  두 번 담아 중복을 만들고, 그만큼 다른 대상을 빠뜨린다.
- "0개"는 휴무일일 수도, 아직 안 그려진 것일 수도 있다 — 한 번 더 기다렸다 다시 센다.

**CRM 자동화 코드가 기본 브랜치(main)에 올라가 있어야 한다.**

### 21:00 본 실행 + 22:30 예비 실행

GitHub 의 schedule 은 지연될 뿐 아니라 부하 시간대엔 **통째로 스킵된다.**
스킵되면 실행 자체가 없어서 **실패 알림도 없다** — 그날 CRM 이 조용히 빠진다.
그래서 cron 을 둘 둔다:

| cron (UTC) | KST | 역할 |
|---|---|---|
| `0 12 * * *` | 21:00 | 본 실행 |
| `30 13 * * *` | 22:30 | 예비 — [automation/guard.mjs](../automation/guard.mjs) 를 먼저 태운다 |

`guard.mjs` 는 `crm_slack_posts` 에서 그날 D+1 발송 상태를 본다.

- ok 가 있고 실패가 없으면 → **건너뛴다**(Playwright 설치 전에 끊어서 1분 안에 종료)
- 실패가 있거나 ok 가 하나도 없으면 → **재실행**
- 조회 자체가 실패하면 → **재실행**(모르면 도는 게 낫다)

재실행이 안전한 근거는 설계에 있다 — 슬랙은 `crm_slack_posts` 의 ts 로 `chat.update` 하고(새
메시지가 아니다), 재발송 억제는 `대상일자 <> targetDate` 라 자기 자신을 억제 근거로 쓰지 않는다.

`schedule` 실행은 `DRY_RUN=false`(반영)로 **명시 분기**되어 있다 — `inputs` 폴백에 의존하지 않는다.
수동 실행의 기본값은 여전히 `dry_run=true` 다.

## 4-1. 🔥 회차·횟수를 말하는 멘트는 "사실 단언"이다 (2026-08-14 사고)

**"구태희님, 오늘로 10번째 수업이에요!"** 가 반포 채널로 나갔다. **실제 출석은 4회.**
같은 날 나간 마일스톤 5건 중 **3건이 틀렸다.**

원인은 스크래핑이 아니라 **집계 공식**이었다. `members` 한 행은 사람도 수강권도 아니고
**(수강권 등록건 × 결제건 × 그때의 이름)** 이다. 같은 수강권 한 장이 여러 행으로 남는다:

| 경로 | 왜 행이 늘어나나 |
|---|---|
| 이름 표식 | `'구태희'` / `'구태희 미수금'` — 표식이 붙었다 떼어지는 사이에 재업로드하면 `dedup_key` 의 `이름` 이 달라 행이 둘. `makePersonResolver` 는 이 둘을 **한 사람으로 합친다** → 합치는 순간 같은 수강권이 두 번 세어진다 |
| 결제 분할 | 미수금 완납·추가 결제로 `결제일시/결제금액` 이 다른 행이 또 생긴다(`KEY_COLS` 설계상 정상) |

⚠️ **이 행들은 같은 잔여횟수를 각자 들고 있다.** 그래서 `Σ (전체−잔여)` 는 한 번 나온 수업을
2~3번 센다. 구태희: 체험권 2행 + 20회권 3행 → `1+1+1+3+3 = 9` → "내일이 10회차".
등록건으로 접으면 `1 + 3 = 4` 로 실제와 일치한다.
**실측 2026-08-19: 전 회원 7,690명 중 583명의 누적이 부풀어 있었다(최대 +615회).**

고친 자리 — 공식은 [shared/crm-core.mjs](../shared/crm-core.mjs) 한 곳에만 둔다:

- `dedupeTicketRows(rows)` — **(수강권명 + 수강권시작일) = 수강권 등록건** 하나에 대표 행 1개.
  대표는 **사용횟수가 가장 큰 행**(출석은 되돌아가지 않는다. `apply_attendance` v2 가 중복 행 중
  1행만 갱신하므로 나머지는 옛 잔여를 든다). 재등록(같은 이름 · 다른 시작일)은 별개 등록건이라
  그대로 더해진다.
- `usageAudit(rows)` → `{누적, 등록건수, 행수, 결손, 시작일결손, 최초시작일}`.
  값 하나가 아니라 **그 값을 믿어도 되는지**를 같이 낸다.
- `personUsedCount(rows)` — 화면(회원 관리 사용횟수 필터 · 회원 요약 총사용)도 같은 함수를 쓴다.
  ⛔️ **행 단위 `Σ usedCount` 금지.**

### 교차검증 — 두 기록이 모순이면 보내지 않는다

`members`(엑셀 + 야간 `apply_attendance`)와 `reservations`(매일 스크랩한 실제 출석)는 **서로 독립적인
두 기록**이다. `verifyMilestone()`([shared/crm-rules.mjs](../shared/crm-rules.mjs))이 대조해서 모순이면
발송을 **보류**하고 경고만 남긴다(실명 없이 건수만 — §6).

| 보류 사유 | 왜 |
|---|---|
| 전체횟수 결손 | 몇 회짜리인지 모르면 사용횟수(전체−잔여)도 모른다 |
| 수강권시작일 결손 | 등록건을 구분할 수 없다 = 중복 행을 접었는지 보장 못 한다 |
| 출석 기록 > 누적 | `members` 가 뒤처졌다(매칭 실패·업로드 지연) → 회차를 **낮게** 부른다 |
| 전 이력 관측 + 불일치 | 첫 수강권시작일이 예약 스냅샷 시작일 이후면 그 사람의 모든 수업이 스냅샷 안에 있어야 한다. 수가 다르면 어느 쪽도 못 믿는다 |

⛔️ **"관측이 적으니 관측 쪽을 쓰자"로 가지 말 것.** 스크랩이 하루 빠지면 관측도 낮아진다.
둘 다 못 믿을 때 지어낸 숫자를 보내는 것이 이 규칙이 막으려는 바로 그 사고다.
보류가 계속 쌓이면 원인(스크랩 누락·엑셀 미업로드)을 고친다. 급하면 규칙 파라미터
`교차검증: false` 로 끌 수 있지만, 그건 **틀린 숫자를 보내겠다는 결정**이다.

**이미 나간 잘못된 메시지는 지워야 한다** — 마일스톤은 '평생 1회' 억제라, 잘못 나간 "10회차"
기록이 남아 있으면 그 회원의 **진짜 10회차** 축하가 영영 억제된다.
정리: `npm run db:backup crm_messages` → `npm run db:sql sql/2026-08_fix_milestone_overcount.sql`
(발송 회차 > 현재 누적 + 1 인 것만 지운다 — 경계에 있는 정상 발송은 건드리지 않는다).

**교훈:** 숫자를 말하는 멘트는 "값이 있다"가 아니라 **"그 값이 무엇의 합인지"** 를 먼저 물어야 한다.
행이 곧 사람이 아니고, 행이 곧 수강권도 아니다.

**도입 초기 14일** 은 `14일 미방문` 규칙이 자동으로 잠긴다. 예약 스냅샷이 없어 "한 번도 안 온
사람"과 "아직 관측 안 된 사람"을 구분할 수 없기 때문이다. 화면에 관측 일수 배너가 뜨고,
관측 이력이 없는 회원은 "미방문"이 아니라 **"모름"** 으로 표기된다.

## 6. 개인정보 원칙

- **슬랙에는 이름 + 수업 정보까지만.** 연락처·생년월일·결제금액은 절대 넣지 않는다
  (채널 인원이 회원 DB 접근 권한자보다 넓다).
- **운영 알림(#ops)에는 건수와 단계만.** 미매칭 로그에는 실명이 섞인다.
- `automation/out/*.json` 은 회원 실명을 담는다 — 커밋 금지, **artifact 업로드 금지**.
- 미매칭 명단 화면에 CSV 내보내기 버튼을 두지 않는다.
- 슬랙은 **발송 전용**이다. 인터랙션(버튼) 엔드포인트를 만들지 않는다 — 서버를 도입하면
  정적 export + RLS 보안 모델이 통째로 바뀐다.
