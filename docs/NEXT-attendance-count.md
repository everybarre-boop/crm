## 왜 하는가 — 지금 무엇이 틀렸나

**한 문장:** 우리는 "출석 횟수"라고 말하면서 실제로는 **"수강권에서 차감된 횟수"** 를 세고 있다.

```
지금:      출석횟수 = 전체횟수 − 잔여횟수        ← members(스냅샷)
필요한 값:  출석횟수 = 예약상태가 '출석'인 수업의 개수   ← reservations(이벤트 로그)
```

이 둘이 같으려면 "차감 = 출석"이어야 하는데, 네 가지가 깨뜨린다.

| # | 원인 | 실측 사례 |
|---|---|---|
| ① | **결석·노쇼도 차감된다** | 안민영(송파): 출석 8 · 결석 1 → 차감 9 → "10번째 수업" 발송. 실제 9번째. 지점별 미출석률 0.3~10.2% |
| ② | **횟수 조정을 되짚을 수 없다** | 명목 10회권인데 `전체횟수`가 1·5·9. 조정 **전에** 몇 번 썼는지 기록이 없다. 전 지점 평균 20%, 송파 33% |
| ③ | **만료 소멸 = 완전 소진** | 기간이 지나면 잔여가 0이 된다. `10회 중 10회 출석`과 `3회 쓰고 7회 날림`이 DB 에서 **완전히 동일**하다 |
| ④ | **스냅샷은 시점 값** | 08-14~08-20 자동화 정지 중 members 가 뒤처진 채로 08-21 발송 |

### 측정 결과 (2026-08-24)

전 이력이 관측 구간(2026-07-29~) 안에 있어 **검증 가능한 회원 137명** 기준:

```
members 누적 == 실제 출석 :  90명 (65.7%)
결석으로 설명되는 차이     :   3명
설명 안 되는 차이(②③)     :  44명
```

**지점별 일치율: 판교 63% · 청담 68% · 옥수 59% · 송파 67% · 반포 75% · 광교 64%.**
→ **지점 차이는 없다.** 규칙 코드에 지점이 들어가는 자리가 아예 없고, 데이터에서도 유의한
차이가 없다. 송파에서만 오류가 눈에 띈 건 그날 마일스톤 대상자가 거기 2명 몰렸기 때문이다.

⚠️ 어긋남은 **양방향**이다. 회차를 높게 부르기도(오발송), 낮게 부르기도(마일스톤 놓침) 한다.

```
누적 > 출석 (높게)  반포 이수연 9/7 · 판교 박수인 11/7 · 판교 곽민지 5/2
누적 < 출석 (낮게)  청담 서재원 5/6 · 옥수 조우인 2/3 · 옥수 박지원 0/1
```

### 왜 지금 구조로는 못 고치나

| | 성질 | 누적을 셀 수 있나 |
|---|---|---|
| `잔여횟수` | 스냅샷 — "지금 몇 개 남았나" | ❌ 과거를 복원할 수 없다 |
| `reservations` 출석 행 | 이벤트 로그 — "이 날 이 수업에 나왔다" | ✅ 정확히 셀 수 있다 |

스냅샷은 **현재 상태**에, 이벤트 로그는 **누적**에 정확하다. 지금은 둘을 바꿔 쓰고 있다.

⛔️ **"관측이 적으니 관측 쪽을 쓰자"로 가지 말 것.** 스크랩이 하루 빠지면 관측도 낮아진다.
둘 다 못 믿을 때 지어낸 숫자를 보내는 것이 교차검증이 막으려는 바로 그 사고다.

## 설계 — 값의 역할을 갈라놓는다

```
출석 횟수 · 회차 · 마일스톤 · 휴면   →  이벤트 로그만 쓴다
남은 횟수 · 만료일 (만료임박)        →  스냅샷만 쓴다   ← 이건 스냅샷이 정답인 값
전체횟수 − 잔여횟수                 →  어디에도 쓰지 않는다   ← 지금 모든 오류의 출처
```

### 관측 구간이 짧은 문제의 해법

**스튜디오메이트가 회원별 출석 수를 직접 세어 보여준다.** 우리가 계산할 필요가 없다.

```
회원 > 이용회원 > 이름 클릭 > 이용내역 탭
  https://everybarre.studiomate.kr/users/detail?id=4633962
  → 전체(17) · 예약(2) · 출석(12) · 결석(0) · 노쇼(0) · 취소(3)
```

그래서:

```
출석횟수 = 기준선(회원 페이지의 '출석' 수, 기준일에 1회 읽음)
         + (기준일 이후 reservations 의 출석 행 개수)
```

두 항 모두 이벤트 기반이고 정확하다. **백필을 몇 시간 돌릴 필요가 없다** — 기준선이 과거를
대신 담는다. 그리고 **스스로 검증된다**: 나중에 회원 페이지를 다시 읽어 우리 계산과 비교하면
어긋남이 즉시 드러난다. 지금의 주간 교차검증을 이걸로 대체한다.

## 구현 단계

### 1단계 — 회원 페이지 스크랩 ✅ 완료 (2026-08-27 라이브 확인)

- ✅ **`?id=` 쿼리가 먹는다** (수업 상세 `?id=` 와 같음. 일정 `?date=` 만 안 먹는다).
- 🔥 **회원 id 는 href 로 못 얻는다 — 위 전제가 틀렸다.** `.members-list-item__name a` 의
  **href 는 null** 이다(Vue 클릭 핸들러). 클릭하면 같은 탭에서 이동해 버려 **행 단위 왕복**이
  되는데, 그건 "8명이 조용히 사라진" 바로 그 사고다.
  → 대신 렌더된 행의 컴포넌트 상태를 읽는다: **`li.__vue__.$props.member.id`**.
  예약자 목록을 통째로 읽는 **같은 `page.evaluate` 한 번**에 같이 읽히므로 왕복 0·추가 요청 0.
  (API 직접 호출이 아니다. `x-sm-signature` 게이트를 흉내 내지 않는다는 결정과 무관하다.)
  검증: 첫 행 `member.id=3205433` ↔ 그 이름을 클릭했을 때 이동 주소 `/users/detail?id=3205433` 일치.
- 🔥 **이용내역 탭은 URL 로 못 연다.** `?tab=history`·`?tab=usage` 둘 다 무시되고 URL 이 그대로다.
  `ul.member-detail__header-tabs li` 중 텍스트가 `이용내역`인 것을 **클릭**해야 한다.
  카운트는 `ul.member-history__header__tabs li` 의 `출석(528)` 형태 텍스트에서 파싱한다.
- ✅ **카운트는 회원 전체·전 수강권 누적이다**(수강권별 집계가 아니다 — 이게 설계의 전제였다).
  조유림(id 940607, 2021-10 등록): `전체 719 = 출석 528 + 취소 191`. '이전 수강권 보기'를
  눌러도 값이 그대로다. `전체(N)` = 예약+출석+결석+노쇼+취소 로 정확히 쪼개진다.
- ⏱️ **회원 한 명 읽는 데 ~1.6초** (실측: 5명 8초 / 4명 6.5초, 로컬 AVG 환경에서).
- 셀렉터는 **[selectors.mjs](../automation/studiomate/selectors.mjs) 에만** 뒀다
  (`SELECTORS.member.*` · `URLS.userDetail` · `MEMBER_ID_VUE_PATH`).
- 구현: [scrape.mjs](../automation/studiomate/scrape.mjs) 의 `scrapeMemberAttendance` / `scrapeMembers`.
  ① 이름 일치 ② 카운트 파싱 성공 ③ `전체 == 합` — **셋을 다 확인**하고, 하나라도 안 되면
  그 회원을 실패로 남긴다(빈 화면을 "출석 0회"로 통과시키지 않는다).

⚠️ **SPA 함정 재발 주의.** 수업 상세에서 겪은 그대로다 — URL 을 먼저 바꾸고 내용은 API 응답
뒤에 다시 그리므로, 로딩 판정을 "요소가 있다"로 하면 **직전 회원의 값을 읽는다.**
반드시 **대상이 일치하는지**(페이지의 이름/id 가 요청한 것과 같은지)로 판정할 것.
그리고 **별도 탭**에서 열 것(같은 탭이면 캘린더가 오늘로 되돌아간다).

⚠️ **사이트별로 따로 읽어 합산한다.** 지점 = 사이트라 김단하님처럼 청담+송파를 다니는 회원은
`everybarre` 와 `everybarre-songpa` 양쪽에 각각 출석 수가 있다. 한쪽만 읽으면 절반이 된다.

규모: 내일 예약자 ~120명 → 러너에서 10~15분 추가 예상.

### 2단계 — `crm_attendance` 테이블 ✅ 완료

[sql/2026-08_attendance_truth.sql](../sql/2026-08_attendance_truth.sql) — 적용 완료(2026-08-27).

설계에서 **바뀐 것 두 가지**:

1. **유니크 키가 `(site, 회원id)` 다** (원안은 `(person_key, site)`).
   스튜디오메이트 회원 id 는 안 바뀌지만 이름·연락처는 바뀐다. id 를 키로 잡아야 개명·번호
   변경 때 행이 갈라지지 않는다. `person_key` 는 조인용으로 같이 저장하고 매번 최신값으로 덮는다.
2. **"한 번 찍는 기준선"이 아니라 "매일 갱신되는 최신 관측치"다.**
   회원당 1.6초면 내일 예약자 전원(~120명 ≈ 3분)을 매일 밤 다시 읽을 수 있다. 그러면
   기준선 노후·스크랩 빠진 날·기준일 당일 저녁 수업 같은 **드리프트가 원천적으로 사라진다.**
   저장은 두 가지 용도로만 남는다 — 그날 읽기에 실패한 회원의 폴백, 그리고 검증·추적.

`결석수`·`노쇼수`·`취소수`도 같이 저장한다. 규칙은 `출석수`만 쓰지만, "왜 차감 횟수와
다른가"를 이 세 값이 설명해 준다(실측: 김미애 출석 49 · **결석 6**).

### 3단계 — 규칙이 이 값을 쓰게 한다 ✅ 마일스톤 완료

- `shared/crm-core.mjs` 의 **`makeAttendanceCounter({rows, reservations, siteOfBranch, keyOf, today})`**.
  순수 함수다(`shared/*.mjs` 의 import 0 원칙 유지). 반환은
  `(person_key) => { 출석, 확실, 사이트수, 기준일 } | null`.
  - **사이트별 행을 더한다** — 청담+송파를 다니는 회원은 양쪽에 각각 출석 수가 있다.
  - 옛 값만 남은 회원은 **그 사이트의 지점들**에서 기준일 이후 출석 행을 더해 메운다.
    사이트를 구분하지 않고 더하면 이중 계수가 된다.
  - 근거가 없으면 `null` — **지어내지 않는다.**
- 마일스톤 회차 = `출석 + 1`. 보류 조건은 두 가지로 단순해졌다:
  근거가 아예 없다(`null`) / 오늘 읽은 값이 아니다(`확실=false`).
- **`attendanceRows` 가 비면 옛 경로(차감 횟수 + `verifyMilestone`)로 폴백한다.**
  도입 첫날·MOCK·테스트가 조용히 깨지지 않게 하기 위한 것이고, 운영에서는 야간 잡의
  `attcount` 단계가 매번 채운다. 폴백 여부는 `stats.회차근거` 와 각 멘트의 `근거.근거출처`
  (`출석기록` / `차감횟수`)로 확인한다.
- 발송 이력에 **`근거.차감누적`** 도 같이 남긴다 — 옛 값과 새 값이 얼마나 벌어지는지 추적용.

  20~30초 걸려 간헐 실패한다(`SCRAPE_NAV_TIMEOUT` 으로 늘릴 수는 있다).
- 백필이 필요하면 `daily-update` 우회 말고 **`backfill.yml`** 을 쓴다. 날짜마다 **순차로**
  던질 것 — `concurrency: studiomate-scrape` 라 동시에 던지면 대기 중인 실행이 취소된다.
